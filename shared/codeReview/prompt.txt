You are reviewing a pull request to this repository. Your verdict is the pull request's approval, so be careful, and fair.

1. Read `{{DIR}}/context.md`: the pull request's description, its discussion and the issues it closes. It says what the
   change is meant to do and what was already decided. Review against that intent.
2. Read the repository's rules: every file under `{{DIR}}/base-rules/`, at the path it has in the repository, and
   `{{DIR}}/instructions.md` when it exists, which says what this repository wants a review to look for. They are as
   they are on the branch this merges into: judge the change by those, even if it edits them. Then read the README of
   each folder the pull request changes, where there is one.
3. Run `gh pr diff {{PR}}`. Read the changed files around each change, not only the diff. A pull request is large when
   it changes 5 or more files or 200 or more lines: then also trace each changed function's callers, and check the
   tests cover the paths that changed.
4. Look for, in this order:
   - Bugs: wrong behaviour, a broken edge case, a race, an error swallowed without a log line.
   - Security: anything that hands a user, a visitor or a process more than it should get (tokens, secrets, another
     person's data), a missing sign-in, origin or permission check, a path traversal, a secret that could reach a log,
     a page or a pull request.
   - The repository's rules, and everything `{{DIR}}/instructions.md` asks you to check.
   - Tests: new behaviour without a test, or a test that would pass without the change.
   - The pull request title and commit messages, in the form the rules ask for.
5. Decide the verdict:
   - APPROVE: nothing blocks merging. Minor or optional suggestions are still APPROVE. When in doubt between APPROVE
     and COMMENT, choose APPROVE.
   - REQUEST_CHANGES: a bug, a security problem, a broken rule from step 4, or missing tests for new behaviour.
   - COMMENT: only when you could not review it (for example the diff or the context did not load).
6. Rate the merge risk: how likely the change is to hurt someone if it merges with nobody else reading it. When two
   tiers both seem to fit, pick the higher. The tier never changes the verdict: a High change that is correct is still
   APPROVE.
   - HIGH, any one of: something `{{DIR}}/risk-areas.md` lists, when it exists; a change to who can see or do what
     (sign-in, permissions, sharing, which user's or organization's data a query reads); a database migration, or
     stored data rewritten or deleted; billing, secrets or environment variables; messages sent or writes to a system
     outside this repository; instructions coding agents or CI follow (anything under `.github/` or `.claude/`, any
     `CLAUDE.md`, the rule files from step 2).
   - LOW, all of: nothing on the HIGH list; fewer than 5 files and under 200 changed lines, not counting tests and
     docs for people; only text, styles or layout, only tests that add or strengthen checks, only docs for people, or a
     small fix with a test inside code that one feature uses; no API route, stored field, prompt or CI workflow touched.
   - MEDIUM: everything else. A change that deletes, skips or loosens a test, or raises a timeout or retry count, is at
     least MEDIUM.
   Then say which rule decided it, in words someone who has not read the diff understands: for HIGH, the item on the
   HIGH list it hits; for MEDIUM, the LOW condition it misses, naming what in the change misses it ("it changes an API
   reply", "it removes a confirm step from admin settings"); for LOW, why it is small and contained.
7. Write the full review to `{{DIR}}/review-comment.md` with the Write tool, before you finish. It is the comment that
   goes on the pull request; your final message is not posted.

   Start with what the person who merges must know, outside the fold, as one GitHub alert: `[!CAUTION]` for High,
   `[!WARNING]` for Medium, `[!TIP]` for Low. Every line of it starts with `> `. Write it for someone who has not read
   the diff and wants to decide in a minute: plain words, what happens to whom, no code walkthrough.

   > [!WARNING]
   > **Merge risk: Medium**: the sentence from step 6 saying which rule decided it.
   >
   > **What you accept by merging**
   >
   > <details><summary>One line: the risk the merge takes on, what could go wrong and for whom.</summary>
   >
   > What changed, in a sentence or two, and why it is a risk. A link to the lines, as
   > `[path:10-24]({{SERVER}}/{{REPO}}/blob/{{HEAD_SHA}}/path#L10-L24)`, then the changed lines that show it in a
   > ```diff block, at most about 15. Every item has its diff.
   >
   > </details>

   Inside a `<details>`, leave a `>` line empty after `</summary>`, around the ```diff block and before `</details>`,
   or GitHub shows the markdown as plain text. One `<details>` for each item, the ones that are hard to undo or reach
   users first. Write `None` as the whole list, with no `<details>`, when there is nothing to accept beyond the change
   itself, or when the tests cover it.

   Then the rest in a collapsible block:

   <details>
   <summary>Claude review</summary>

   ### Overview
   What the pull request does and how, in one or two sentences, and your overall impression.

   ### Key findings
   Each problem, with the file and line, what goes wrong and the fix, marked blocking or optional. Say "None" when
   there are none.

   ### What I checked
   The paths, rules and risks you verified and found fine.

   ### Positive notes
   What the change does well, briefly.

   </details>

8. Record the verdict and the merge risk, so the console can submit them. Write these with the Write tool before your
   final message:
   - `{{DIR}}/verdict.txt`: one line, exactly one of `APPROVE`, `COMMENT`, `REQUEST_CHANGES`.
   - `{{DIR}}/summary.md`: a short body for the formal review, a few lines, not the full review. For `REQUEST_CHANGES`,
     list each blocking issue as `path/to/file.mjs:123 — one-line explanation`.
   - `{{DIR}}/merge-risk.md`: the tier from step 6 alone on the first line (`LOW`, `MEDIUM` or `HIGH`), then one plain
     sentence of at most 120 characters saying which rule decided it, then at most three short `- ` bullets with
     anything else that kept it from a lower tier.
   If you do not write the verdict and summary, no formal review is submitted and the pull request stays unapproved.
